# FVW – 0.2.175

## تغییرات رابط استوری‌بورد
- اعمال خودکار بازه و فاصلهٔ فریم‌ها، دو ثانیه پس از پایان ورود متن زمان.
- انتقال All View به ردیف بالای جدول استوری‌بورد.
- انتقال تیک «نام‌گذاری اختیاری» به سمت راست پلیر.
- Fit متن با حفظ کامل کلمه‌ها و شکست سطر فقط بین کلمه‌ها.
- پرکردن فضای قابل استفاده جدول در هر دو حالت عادی و All View.


## موتور ترکیب چندویدیویی (مرحلهٔ اول)
- فایل‌های افزوده‌شده به ردیف مستقل VIDEO اکنون در خروجی نوار ترک‌ها روی ویدیوی اصلی ترکیب می‌شوند. هر قطعه از زمان مبدأ انتخاب‌شده بریده می‌شود و در زمان شروع خودش نمایش داده می‌شود.
- چند ویدیو می‌توانند هم‌زمان نمایش داده شوند؛ هر کدام به‌صورت کاشی کوچک با حفظ نسبت تصویر در یکی از چهار گوشه قرار می‌گیرد.
- صدای ویدیوی اصلی، ترک‌های AUDIO و صدای همراه کلیپ‌های VIDEO در صورت وجود با هم میکس می‌شوند. زیرنویس‌ها در مسیر نگاشت قبلی باقی مانده‌اند.
- این مرحله فقط مسیر خروجی مستقل نوار ترک‌ها را پوشش می‌دهد؛ ترکیب با همهٔ افکت‌های تصویری هنوز در مرحلهٔ بعد است.

## موارد قطعیِ تکمیل‌نشده
- کنترل مستقل موقعیت و اندازه برای هر ویدیوی رویی هنوز وجود ندارد؛ جایگاه فعلی خودکار و چهارگوشه‌ای است.
- ترکیب ترک‌های VIDEO با Crop، رنگ، متن و افکت‌های سراسری در یک خروجی واحد هنوز انجام نمی‌شود.
- کدک/کیفیت خروجی هنوز قابل انتخاب نیست و بیلد APK و آزمون روی دستگاه Android/ARM32 باید انجام شود.

جزئیات کامل تغییرات و مراحل بعدی در `VWork_Update_Notes_FA.txt` ثبت شده است.

## Version 0.2.131 — Timeline audio/subtitle lanes

- Added a two-lane horizontal track area under the video timeline: AUDIO and SUBTITLE.
- Audio and subtitle pickers allow selecting multiple files. Each selected file appears as a separate clip starting at the current playback position.
- Drag a clip body to move it; drag its left/right edge to trim it. Select a clip and use **برش ترک در محل پخش** to split it at the current playback position; each half can then be moved/trimmed independently. **حذف قطعه** deletes the selected piece and **پاک‌کردن ترک‌ها** clears the track area.
- For track-only exports, the source video stream is copied without video re-encoding. Added audio clips are mixed with the original audio and limited to the source video duration. Subtitle clips are mapped as subtitle streams with timeline offsets; MP4 uses `mov_text`, while MKV copies subtitle streams when supported.
- Current limitation: timeline track placement is exported through the dedicated track-only path. Combining those positioned clips with visual effects/crop/text in one output is not yet supported; the app warns instead of silently ignoring track positions. Subtitle trim behavior depends on the subtitle container/format and should be tested with the specific file.
- Android Gradle build/device install was not run in this environment.

# EVCtow 0.2.130 — حفظ کدک ویدیو هنگام افزودن صدا یا زیرنویس

## Version 0.2.130 — حفظ کدک اصلی ویدیو
- در خروجی‌هایی که فقط صدای خارجی یا زیرنویس اضافه می‌شود، جریان تصویر با `-c:v copy` منتقل می‌شود تا کدک اصلی ویدیو دوباره رمزگذاری نشود.
- صدای اصلی در حالت بدون جایگزینی با `-c:a copy` حفظ می‌شود. صدای خارجی، در مسیر فعلی جایگزین صدای اصلی است و برای سازگاری به AAC تبدیل می‌شود؛ این تبدیل روی جریان تصویر اثری ندارد.
- در MP4، زیرنویس در صورت نیاز به `mov_text` تبدیل می‌شود؛ در MKV، جریان زیرنویس کپی می‌شود.
- برش تصویر، تغییر رنگ، Auto Color، درج متن یا ویدیوی رویی همچنان به رمزگذاری مجدد تصویر نیاز دارند.
- اگر کدک اصلی با ظرف خروجی انتخاب‌شده سازگار نباشد، کپی مستقیم ممکن است شکست بخورد؛ در این حالت باید ظرف خروجی سازگار انتخاب شود.
- کنار نوارهای قرمز، سبز، آبی و اشباع رنگ، دکمهٔ `Rest` اضافه شد؛ هر دکمه فقط همان نوار را به مقدار خنثی `1.00` برمی‌گرداند.
- دکمهٔ Rest اشباع رنگ کمی برجسته‌تر و عریض‌تر است تا سریع‌تر پیدا شود.
- در پنجرهٔ «ویرایش پیشرفته» نیز برای نور، کنتراست و گاما دکمهٔ Rest جداگانه کنار هر نوار اضافه شد؛ مقدار اولیهٔ هر کنترل بازگردانده می‌شود.
- این تغییر فقط کنترل‌های بازنشانی را اضافه می‌کند؛ نور، کنتراست و گاما در نسخهٔ فعلی هنوز به موتور خروجی متصل نشده‌اند.
- XML و ZIP بررسی می‌شوند؛ بیلد اندروید و آزمایش روی دستگاه در این محیط انجام نشده است.

## راهنمای Commit و GitHub Actions

راهنمای EVeditor برای جلوگیری از مشکل نمایش ندادن Commit در GitHub Actions و MGit
---

۱) چیدمان درست مخزن
- فایل ZIP را طوری استخراج کنید که پوشه‌های app و .github و فایل‌های build.gradle.kts و settings.gradle.kts مستقیماً در ریشه مخزن باشند.
- مسیر فایل بیلد باید دقیقاً این باشد:
  .github/workflows/android.yml
- اشتباه رایج: قرار گرفتن فایل‌ها در یک پوشه اضافی، مثل EVeditor/EVeditor/.github/...
- این بسته برای مخزن تازه آماده شده و تاریخچه/پوشه .git قبلی را حمل نمی‌کند.

۲) تنظیم فعلی Workflow در EVeditor
فایل android.yml از قبل این محرک‌ها را دارد:
  on:
    push:
      branches: ["**"]
    pull_request:
      branches: ["**"]
    workflow_dispatch:

یعنی Push به هر شاخه باید Workflow را اجرا کند؛ بنابراین محدودیت قدیمی main/master در این نسخه وجود ندارد.
فایل YAML را بدون نیاز تغییر ندهید. نام شاخه MGit را فقط برای بررسی یادداشت کنید.

۳) ساخت مخزن و Push اولیه
- در GitHub یک مخزن خالی با نام EVeditor بسازید. هنگام ساخت، گزینه افزودن README یا .gitignore را فعال نکنید تا با فایل‌های پروژه تداخل نکند.
- در MGit، پوشه‌ای را انتخاب کنید که app و .github و فایل‌های Gradle مستقیماً داخل آن هستند.
- شاخه را بررسی کنید (مثلاً main یا master).
- همه فایل‌های پروژه را Stage کنید.
- یک Commit واقعی با پیام مانند Initial EVeditor project بزنید.
- سپس Remote مربوط به مخزن GitHub را اضافه کنید و Push را به همان شاخه انجام دهید.
- صرفاً ذخیره فایل‌ها یا ایجاد Commit محلی، اجرای GitHub Actions را شروع نمی‌کند؛ Commit باید با موفقیت Push شود.

۴) اگر Commit در تاریخچه دیده می‌شود ولی Actions اجرا نشده است
به ترتیب بررسی کنید:
الف) در GitHub > Code مطمئن شوید فایل .github/workflows/android.yml در ریشه مخزن قرار دارد.
ب) محتوای فایل را باز کنید و وجود push.branches: ["**"] و workflow_dispatch را بررسی کنید.
ج) در GitHub > Actions ببینید Workflow با نام EVeditor Android Build فهرست شده است یا نه.
د) در Settings > Actions > General، اجرای GitHub Actions برای مخزن مجاز باشد.
هـ) در MGit مطمئن شوید Push بدون خطا انجام شده و شاخه مقصد همان شاخه‌ای است که در GitHub مشاهده می‌کنید.
و) اگر Workflow دیده می‌شود ولی اجرا نشده، از Actions > EVeditor Android Build > Run workflow اجرای دستی را امتحان کنید.
ز) اگر اجرا شده و قرمز است، آن دیگر مشکل «شروع نشدن Workflow» نیست؛ وارد همان Run شوید و نخستین خطای واقعی در Build Android را بررسی کنید.

۵) تفاوت سه وضعیت مهم
- Commit فقط در MGit: محلی است و GitHub از آن خبر ندارد.
- Commit در GitHub > Commits، بدون Run در Actions: معمولاً باید محل Workflow، مجاز بودن Actions، شاخه و تریگر بررسی شود.
- Run در Actions با علامت قرمز: Workflow شروع شده اما یکی از مراحل Build یا دریافت وابستگی‌ها شکست خورده است.

۶) نکته‌های مهم
- فایل android.yml را حذف یا به پوشه‌ای غیر از .github/workflows منتقل نکنید.
- نام مخزن GitHub لازم نیست با نام داخلی Gradle یکسان باشد، اما برای نظم این پروژه هر دو EVeditor هستند.
- این پروژه از JDK 17 و Gradle 8.9 استفاده می‌کند و هدف فعلی آن فقط ABI سی‌ودوبیتی armeabi-v7a است.
- حداقل Android پروژه API 24 است.
- پس از Push موفق، در صورت موفقیت بیلد، فایل APK را از بخش Artifacts همان اجرای Workflow دریافت کنید.
- این راهنما تضمین نمی‌کند هر Build حتماً موفق شود؛ فقط مسیر تشخیص مشکل اجرا نشدن Commit/Workflow را مشخص می‌کند.


## آماده‌سازی مخزن VWork برای GitHub و MGit
- نام مخزن و ریشه Gradle: `VWork`
- نام Workflow: `VWork Android Build`
- نسخه برنامه: `0.2.167` و versionCode برابر `367` (از `app/build.gradle.kts`)
- Workflow روی Push و Pull Request به همه شاخه‌ها فعال است (`branches: ["**"]`) و اجرای دستی `workflow_dispatch` نیز دارد.
- این ZIP برای ایجاد مخزن تازه آماده شده و پوشه `.git` و Remote/تاریخچه قبلی در آن وجود ندارد.
- نام نمایشی نصب برنامه `EVeditor` و شناسه `com.evc.app` عمداً حفظ شده‌اند تا هویت نصب برنامه تغییر نکند.
